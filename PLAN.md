# PLAN.md - Telecom KPI Monitor

Build plan for a 4G LTE / 5G NR network KPI and alarm monitoring dashboard (NOC-style). This document is the single source of truth for scope; the code in this repo is currently a scaffold (app shell, page placeholders, data model). Anyone can pick up a milestone below and implement it.

## 1. Goal

Give a network analyst one browser tab that answers, for a small synthetic radio network:

1. Which cells are degraded right now (call drops, latency, throughput, congestion)?
2. Which alarms are active, how severe are they, and which KPI drops do they explain?
3. What is happening on the transport side (protocol mix, retransmissions) for a given capture?

Non-goals: no live OSS/NMS integration (SolarWinds, NetAct, etc.), no authentication, no backend. Everything runs client-side on synthetic data so it can be hosted as a static site.

## 2. Tech stack

| Layer | Choice | Reason |
| --- | --- | --- |
| Build | Vite 5, TypeScript 5 | fast, zero-config, strict types |
| UI | React 18 | component model already used across the author's other projects |
| Routing | hash-based page switch (current) -> `react-router-dom` when pages get URL params (M2) | shareable links to a cell / alarm |
| Charts | Recharts | simple time-series and bar charts, no D3 boilerplate |
| Tables | plain `<table>` + small sort/filter hook; TanStack Table only if row counts demand it | keep bundle small |
| State | React context + `useReducer` for filters and time range | no external store needed |
| Data | static JSON in `src/data/`, generated by `scripts/generate-synthetic-data.mjs` with a fixed seed | reproducible, no backend |
| Tests | Vitest for KPI math and data loaders; Playwright smoke test per page | keep the KPI formulas verified |
| Hosting | Vercel (static) | already deployed at https://telecom-kpi-monitor.vercel.app |

## 3. Data model (`src/types/telecom.ts`)

- `Site { siteId, name, lat, lon, region }`
- `Cell { cellId, siteId, technology: "LTE" | "NR", band, bandwidthMHz, azimuthDeg }`
- `KpiSample { cellId, timestamp, callDropRatePct, rrcSetupSuccessPct, handoverSuccessPct, dlThroughputMbps, ulThroughputMbps, latencyMs, prbUtilizationPct, rsrpAvgDbm, sinrAvgDb, activeUsers }` - one row per cell per 15-minute interval
- `Alarm { alarmId, timestamp, siteId, cellId?, severity, probableCause, state, clearedAt? }`
- `PacketStat { protocol, packets, bytes, retransmissions? }`

KPI formulas (also in README):

- CDR % = dropped / (dropped + completed) x 100
- RRC setup success % = successful setups / attempts x 100
- Handover success % = successful HOs / attempts x 100
- PRB utilization % = used PRBs / available PRBs x 100
- Latency = user-plane RTT (ms); Throughput = DL/UL MAC throughput (Mbps)

Default thresholds (editable in the UI, stored in `localStorage`):

| KPI | Warning | Critical |
| --- | --- | --- |
| CDR | > 1.0 % | > 2.0 % |
| RRC setup success | < 98 % | < 95 % |
| Handover success | < 97 % | < 94 % |
| Latency | > 40 ms | > 60 ms |
| DL throughput (LTE / NR) | < 15 / < 80 Mbps | < 8 / < 40 Mbps |
| PRB utilization | > 70 % | > 85 % |

## 4. Synthetic dataset spec (`scripts/generate-synthetic-data.mjs`)

- Seeded PRNG (mulberry32, seed `20260923`) so every run produces identical files.
- **Sites**: 12 sites named after Visakhapatnam localities (e.g. `VSKP-001 Gajuwaka`), lat/lon jittered around 17.69 N, 83.22 E; 3 regions.
- **Cells**: per site 3 LTE cells (bands B3 / B40 / B1, 20 MHz, azimuths 0 / 120 / 240) + 1 NR cell (n78, 100 MHz) = 48 cells.
- **KPI samples**: 7 days x 96 intervals x 48 cells = 32,256 rows. Baselines per technology with a daily traffic curve (peak 19:00-22:00 local): PRB utilization follows the curve; latency and CDR rise with utilization; throughput falls with utilization. Add Gaussian noise (sigma = 5 % of baseline).
- **Injected incidents** (so the dashboard has something to find):
  1. Cell outage: `VSKP-004-L2` down 6 h on day 3 -> Critical "Cell down" alarm, KPIs null during outage.
  2. Congestion: `VSKP-007-N1` PRB > 90 % every evening on days 4-7 -> Major "High PRB utilization" alarm, CDR 3-4 %.
  3. Transmission fault: site `VSKP-010` latency 120-180 ms for 2 h on day 5 -> Major "Transmission link degraded".
  4. Antenna fault: `VSKP-002-L1` RSRP -12 dB, HO success 88 % on days 6-7 -> Minor "VSWR high".
- **Alarms**: ~300 total; the four incident alarms above plus random Minor / Warning alarms (e.g. "Battery on discharge", "Door open", "Temperature high", "Sleeping cell suspected"). States: 70 % cleared, 20 % active, 10 % acknowledged.
- **Packet stats**: one protocol-hierarchy table for a synthetic S1-U / N3 capture: GTP-U, S1AP, NGAP, SCTP, TCP, UDP, DNS, SIP, RTP, ICMP; ~1.2 M packets, byte counts consistent with typical payload sizes; TCP retransmission rate 0.8 %. Also a `top_conversations` array (20 rows).
- Output: `src/data/{sites,cells,kpi_15min,alarms,packet_stats}.json`. `kpi_15min.json` is ~5 MB; if too large for the bundle, split by day and lazy-load.

## 5. Pages and features

### 5.1 Overview (`/`)
- Global time range (1h / 24h / 7d) and technology filter (All / LTE / NR).
- KPI cards: CDR, RRC setup success, HO success, DL throughput, UL throughput, latency, PRB utilization; each shows the network-wide value, delta vs previous window and a sparkline.
- Active alarms by severity with counts; click -> Alarms page filtered.
- "Worst 10 cells" table ranked by CDR, with congestion (PRB) and latency columns.

### 5.2 KPIs (`/kpis?cell=...`)
- Cell / site / technology selectors.
- Time-series chart per KPI with threshold bands and breach markers.
- KPI table for the selected scope with sort and CSV export ("network performance report").
- Compare mode: overlay two cells.

### 5.3 Alarms (`/alarms`)
- Table: time, site, cell, severity, probable cause, state, duration.
- Filters: severity, state, technology, site, free-text.
- Acknowledge / clear actions (client-side, persisted in `localStorage`) with an audit list.
- "Explain" panel: for a selected alarm, show the KPI series of the affected cell in a +/- 2 h window to show the correlation between the fault and KPI degradation.

### 5.4 Packets (`/packets`)
- Protocol hierarchy table and stacked bar (bytes by protocol).
- Top conversations table.
- TCP retransmission and RTT summary tile as a QoS indicator.
- File input to load a user-supplied JSON produced by `tshark -T json` or a CSV export from Wireshark (parser in `src/lib/pcapJson.ts`).

### 5.5 Settings (in a drawer)
- Threshold editor (table above), reset to defaults.
- Theme: light / dark / system.
